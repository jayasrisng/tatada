## Local preview

`TATADA_DEV_PORT=5180 npm run dev:offline` builds the production application shell and runs the private local live backend. Stop the previous Tatada launcher using that port before starting this command; do not run two processes writing the same `.data/server-live.json`. Normal `npm run dev` retains hot reload but deliberately does not claim cold offline support. Explicit download requires HTTPS or loopback, service workers and IndexedDB.

## Hosted parity and deployment

1. Use a private staging project first. Back up the runtime row and stable sealing secret through owner-controlled private storage. Never add these files to `dist`, a PR, diagnostics, or the repository.
2. The current Postgres runtime adapter stores a single JSON state under an existing database lease. `shares` and hosted Gmail exchanges are **optional additive JSON fields**, so this change requires **no SQL migration**. Do not drop/reset the database or replay the base schema over an existing project. Keep `supabase/schemas/tatada.sql` ownership/service-role restrictions unchanged. A new installation needs the existing schema and functions installed by the owner.
3. Configure runtime secrets: stable `TATADA_SECRET` (32+ characters; keep the existing value), `TATADA_APP_URL`, Wajo resource/registered OAuth settings, optional `CLAUDE_API_KEY` or `ANTHROPIC_API_KEY` and `CLAUDE_MODEL`, Google credentials, optional Amadeus credentials/environment. Supabase URL/service-role credentials stay server-side. Do not rotate the sealing key as part of deployment.
4. Hosted Google redirect URI is exactly `https://<project>.supabase.co/functions/v1/tatada-api/api/gmail/callback`; configure this in both Google Cloud and `GOOGLE_REDIRECT_URI`. Local callback is the selected frontend origin plus `/api/gmail/callback`. The local `.env` does not automatically configure hosted secrets.
5. Deploy the reviewed `tatada-api` and `tatada-events` functions with their existing authenticated-route design and verify_jwt settings. Do not expose runtime tables to public roles. CLI commands must be checked against the installed CLI `--help` before execution.
6. Build the actual connected frontend explicitly: `VITE_ENABLE_BACKEND=true npm run build:website`. The default public build otherwise remains the disclosed browser-only app. Publish only `dist/`, including `sw.js`, to `/tatada/`. Serve `sw.js` with revalidation/no-cache and the correct JavaScript MIME type. No source, `.data`, `.env` or user files should be served.
7. Confirm staging health, correct origin/CORS, Wajo browser-bound session exchange, invalid nested workspace rejection, second-device stale-write conflict review, optional research, Google callback tab/account binding, reviewed share creation/public viewing/revocation, account export/deletion and a fresh offline cold launch. An unconfigured optional service must give a visible error. Amadeus test data must remain labeled.
8. Research is read-only and runs outside the 90-second mutation lease; it cannot modify workspace state. Returned research must still be saved by the authenticated versioned workspace route. Gmail/print mutations retain the persistence-before-side-effect barrier. Hosted timing and quotas need staging measurement.

[Supabase environment-variable documentation](https://supabase.com/docs/guides/functions/secrets) was checked. [Changelog](https://supabase.com/changelog) was reviewed: the November 10 TLS cipher retirement needs modern clients, while this continuation does not alter SQL, legacy pgcrypto encryption, .NET or Management API logging.

## Rollback

Keep the prior frontend bundle and function version in private release storage. Pause new provider actions; allow active/uncertain requests to settle before rollback. Restore application code first, retaining the existing runtime state and sealing secret. Because fields are additive, the old backend can ignore new optional fields; however, the **old frontend's workspace validator does not recognize new booking/time-zone/proposal fields**. Do not open current browser state with the old frontend: export first and use a new staging origin to inspect rollback compatibility. Prefer a forward fix. Never overwrite newer personal workspaces with an old whole-database snapshot without explicit owner review. Existing downloaded static shells can remain installed; verify the replacement shell activates before certifying a rollback. Revoke any externally reachable share links before rolling back to code that cannot manage them.

## Retention and deletion

- Active workspaces, conversations, actions and uploaded print jobs remain until explicit deletion or the existing bounded print retention. The print list shows the latest 20 jobs/account; preparation prunes older inactive records beyond 40 and inactive PDFs beyond the latest five. Active or uncertain sends are retained until resolved. Confirm actual provider and hosting retention separately.
- Confirmation originals use a **separate** IndexedDB database and a non-extractable browser device AES-GCM key. This protects stored bytes, not access by someone using the unlocked browser workspace. Originals are not synced/backed up by account export. Download them individually; profile → account data → original confirmations also lists retained files after a reservation is removed, with independent download/deletion. Deleting an original invalidates its offline pack entry. Removing a downloaded pack leaves source originals available beside reservations.
- Passport/visa vault remains passphrase-encrypted, separate, auto-locking, and excluded from ordinary export, sync, service-worker caches and offline packs. Account deletion offers a checked-by-default option to delete that workspace's device vault too. Export its encrypted backup first.
- Download packs contain deliberately selected trip essentials including reservation codes and private itinerary notes. They are private device copies, never friend snapshots. They remain until remove-download, signed-in account sign-out, account cleanup or browser storage removal. Anyone using this browser can read them. No authentication token or decrypted vault file is cached.
- Share links are fixed reviewed snapshots, expire after 30 days, and check revocation/expiry/owner existence on every view. Tokens are stored only as hashes. Revocation stops future server access; it cannot remove screenshots or downloads. Revoked/expired snapshot records remain in active server storage until account deletion; there is no automatic erasure promise.
- Account deletion pauses pending workspace sync, refuses unresolved active/uncertain external jobs, removes active workspace, actions, chats, shares, printer/print jobs, stored credentials and sessions. It clears this workspace's browser state/recovery/offline packs and originals. Other accounts and other devices are not erased automatically. Provider authorization/history and previously exported/downloaded files are outside Tatada's control. A localhost owner's API key remains in the operator's `.env`; remove/revoke it separately if retiring the local installation.
- Existing `.data/e2e-backups/` and any operator filesystem/hosting backups are not automatically erased. Their configured retention is **not verified**. Before public release, the owner must choose/document a backup expiry period and deletion procedure, including reapplying deletions after restores. Do not advertise immediate erasure from all backups.
- Logs added here retain event names, status/error class and synthetic fixture metadata; no request bodies, query contents, provider error text, tokens or private account data. Append-only verification history remains intentionally retained. Earlier provider diagnostic records were not republished or altered.
