# Tatada repository review — October 17, 2026

## What the product is today

A browser-only travel organizer with a distinctive chalkboard interface. React screens cover onboarding, a draggable home canvas, trip creation, phase-based checklists, research comparisons, a journal, outfit suggestions, and printable summaries with QR codes. A shared reducer coordinates these features; localStorage holds all user data.

The strongest product idea is the action approval experience: inspect the proposed recipient, script, shared information, cost, and risk; approve; answer a follow-up question; inspect the outcome. This is implemented as a local, timer-driven simulation. There is no deployed backend, account authentication, live research, Claude call, or Fo execution in the application source.

## Biggest gaps, in priority order

| Priority | Gap and consequence | Concrete next step | Acceptance check |
| --- | --- | --- | --- |
| P0 before live execution | Approval and verification currently live entirely in an editable browser. Sample evidence is generated by the same simulator that claims success. | Build a narrow server action API with authenticated ownership, immutable approved content, an idempotency key, durable transitions, and an audit trail. Keep credentials server-side. Require provider evidence for verification. | Repeated approval requests execute once; edits require new approval; a provider timeout cannot become verified. |
| P1 | Magic uses substring matching and Lisbon-specific recipients, dates, party sizes, and booking references regardless of the selected trip. New trips receive empty research options. | Separate demo scenarios from a trip-aware planner. Define validated request/result contracts using the selected trip and profile. Ask for missing recipient/date information before proposing an action. | Create a Kyoto trip with different dates and travelers; no Lisbon recipient or reference appears. An ambiguous request asks a question. |
| P1 | No real integration or durable worker. The Fo document describes an intended bridge, not working application code. | Ship one vertical slice: connect the user's Fo account, propose one email, approve the exact content, enqueue execution, expose progress and unresolved questions, then attach actual evidence. Confirm capabilities through the official integration contract. | The server can resume after restart and display failure, timeout, and needs-input states without sending twice. |
| P1 | All trips, conversations, and personal notes exist only in browser storage. Clearing the browser loses them; there is no sync, export, restore, or deletion workflow. | Add JSON export/import first, then accounts and owner-scoped database records, schema migrations, retention controls, and backups. | Export/import round-trips a trip; two accounts cannot access each other's records; a second device sees saved changes. |
| P2 | Validation and error recovery are incomplete: missing trip routes render little or nothing; trip dates default to fixed December dates; QR generation has no rejection handling. | Add explicit not-found and error states, rolling date defaults, calendar validation, and QR fallback text. | Unknown trip links offer recovery; invalid dates cannot create a trip; QR failure leaves a usable print view. |
| P2 | Magic declares itself a modal but lacks focus trapping/restoration and background inertness. Some content is hardcoded to Lisbon, including Style and the home dinner card. | Implement dialog keyboard behavior, add a selected-trip context for these screens, and test keyboard and screen-reader flows. | Tab stays within Magic, Escape closes it, focus returns to the opener, and trip-specific content follows the selection. |
| P2 | The existing browser smoke script mainly navigates and takes screenshots; its drag test does not assert persistence. | Add behavioral assertions for reload, new trip creation, task editing, cancellation, context switching, and storage recovery. ## Changes made in this review

- Preserved the supplied application as an initial baseline commit; the remote had no refs when inspected.
- Extracted the reducer from React so the domain behavior can be tested directly.
- Restricted approvals to nonempty simulated proposals; duplicate approval and invalid answers cannot restart progress.
- Restricted answers to the active question's offered options; completed/cancelled actions cannot be replayed.
- Required nonempty result evidence before marking a simulated action verified. This validates evidence presence, not authenticity; real evidence still needs server-side verification.
- Prevented the simulator from approving or advancing real actions.
- Cleared the task association when switching Magic's trip context, avoiding completion of the old trip's task.
- Replaced short Math.random identifiers with 128-bit browser-generated random identifiers, including support for LAN HTTP.
- Added nested saved-state validation, invalid-data backup, guarded storage access/writes, and visible storage warnings. Shape validation is not a migration system or a security boundary.
- Added dependency-free regression tests and GitHub Actions for tests and production builds.

## Recommended shipping scope

Finish one trip-aware email-request flow before expanding features. The user should be able to create a trip, supply a real accommodation contact, review a message grounded in their trip, approve it, and see the actual reply or an honest failure state. That slice tests the value proposition and the difficult integration boundaries together.
